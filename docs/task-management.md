# Task management architecture

`src/tasks/` owns task provenance, membership, lifecycle, context selection, storage, and retrieval. Delivery, voice, delegation, and Pi submit application-owned records or consume projections. They do not choose the most recent task as a destination.

## Trusted provenance

Acceptance allocates a stable request ID from the durable receipt identity before classification. Events retain their parent scope, origin, request and command relationships, receipt/native identities, content references, visibility, and delivery evidence. Reserved internal receipt IDs belong to server-owned delivery paths; the public typed-message endpoint accepts UUIDs. A marker in message text cannot establish an internal origin.

Pi writes metadata-only binding intents before appending native user records. Exact object fingerprints include the native timestamp; missing or conflicting matches remain unresolved. Assistant output records retain the application-owned run and consumed request identities. Session ancestry alone is chronological evidence, not proof that an output answers the latest user message. Multiple work origins must establish the same task set before automatic attachment; otherwise the output remains unresolved. Tool results follow exact native call ownership.

The awaited Pi tool hook records delegate command origins before dispatch. Each managed command inherits its own request identity or retains ambiguous origins. Reusing a saved Side Pocket does not reuse a permanent task assignment. Reports, native questions, and output records retain their producing command where known. A result can therefore reconnect after unrelated input, classification, or restart.

Voice carries the latest observed user speech and bounded current-call references separately from saved startup history. These references help interpret brief answers and cancellations; incomplete speech remains incomplete. Saved history is historical context, and recovery is operational context. Scheduled input follows the application-owned occurrence identity and authorized instruction. None of these distinctions depend on prose markers.

## Classifier ownership and audit

[`classifier-definitions.ts`](../src/tasks/classifier-definitions.ts) is the shared audit point for every task classifier: model, endpoint, deadlines, versions, thresholds, input limits, static predicates, and dynamic task/evidence/question predicate instructions. Intent and lifecycle use the same validated transport in `classifier-client.ts`. Retention capacity and settled-command policy are explicit in the same definitions module; their transitions remain pure.

The main agent executes authorized work. The task subsystem maintains membership and lifecycle independently; it does not depend on the main agent remembering to update task status. Source changes coalesce into a background review after 250 ms, and main-turn settlement schedules another review. The ten-minute timer remains a recovery fallback. Ingestion continues during provider calls; new input preempts them. Neither acceptance nor the working agent waits for classification.

## Routing and interpretation

Deterministic routing follows known requests, commands, and calls first. Missing correlation produces a retained diagnostic. Classification interprets only current intent that lacks an established relationship, using bounded original task descriptions, explicit summaries, pending questions, bounded recent request updates, and relevant references. Archived tasks remain eligible. It never compares a candidate with an accumulating matched transport set.

The semantic outcomes are attachment, creation, conversation only, and needs resolution. Predicate probabilities above the acceptance threshold support a decision; uncertain and conflicting matches remain unresolved. A message discussing multiple tasks can receive explicitly reviewed content spans. Short instructions such as `stop` remain actionable in context. Greetings and acknowledgments do not automatically create tasks.

Each assignment retains its source, policy/classifier version, input revision, task revisions, supporting confidence where available, bounded rationale, and superseded decisions. Provider probabilities are not calibrated accuracy guarantees. Background interpretation holds no persistence lock during a provider call and discards stale results when new acceptance changes the input revision. Provider failures leave the request eligible for another pass.

## Independent state dimensions

- Work: `open`, `waiting`, `resolved`, or `canceled`.
- Retention: `active` or `archived`.
- Delivery evidence: `not_delivered`, `delivered`, or `uncertain`.
- Membership: event-to-task associations, optionally with original-text spans.

A dedicated lifecycle classifier assesses current authorized requirements against exact recorded results and later request updates. Recorded unanswered native questions and unsettled per-command execution facts establish waiting without semantic guessing. Delivered ordinary questions can also be tracked through explicit classifier predicates; later answers are assessed against those exact questions. Active main work, unanswered questions, truncated required intent, and missing required delivery block automatic resolution. Failed tools and bookkeeping acknowledgments do not qualify as successful result evidence. Semantic fulfillment remains the dedicated classifier's assessment, rather than a guarantee supplied by a confidence score. A finished model turn or a prose claim of completion is insufficient.

A resolution records its evidence basis, verification statement, delivery requirement and supporting task-member event IDs. Later explicit user acceptance or an actually delivered answer can supply the appropriate basis; a claim about an external action is not proof that the action happened. Classifier probabilities, source fingerprints, input/task revisions, versions, outcomes and diagnostics are retained in append-only lifecycle reviews. Unchanged evidence is not repeatedly classified. Stale source or command-state snapshots are discarded. Corrections reopen work and restore active retention.

Delivery means confirmed availability in the canonical chat, not proof that the user read it. Both explicit `pocket_send_to_chat` results and persisted ordinary Pi replies use application-owned identities and the phone's visibility boundary. Exact native correlation is required for ordinary replies. Private voice backend output does not establish chat delivery. Restart reconciliation recovers confirmed delivery without replaying any content. Legacy delivery stays uncertain when evidence is missing.

Archiving follows a separate deterministic context policy. It retains up to two recent terminal tasks and retires older terminal context when that capacity or the 24,000-character context budget is exceeded. Open or waiting tasks are never automatically archived. Explicit archiving can defer unfinished work without declaring completion.

The context planner preserves active requests, later constraints, questions, and relevant command identities independently of grouping. Archived unfinished work retains compact identities and pending questions, while its full intent and command history stay available through inspection. Frozen voice transport history is excluded from lifecycle request evidence; current observed intent and bounded current-call references remain separate. Native model calls receive this protected context, including after auto-compaction. Compaction is refused when the protected context exceeds the explicit budget. Oversized protected work stays intact; the model receives a small navigation packet pointing to paged inspection rather than another copy of the oversized context. There is no nonmatch-based closure or grouping-triggered compaction.

## Ledger and projections

Each parent has a private `tasks/<parent-hash>/ledger.sqlite`. An immediate SQLite transaction commits membership, decisions, correlations, lifecycle changes, and source checkpoints together. Expected revisions reject stale writes. Original events, decisions, and correlation records remain immutable; corrections append history. Exact native sources are installed once through an atomic exclusive link, and an interrupted cursor commit reuses the original source sequence and bytes.

Generated task Markdown includes original intent, work and retention state, delivery evidence, current summary, pending questions, delegate assignments, member timeline previews, and links to originals. A separate chronological view makes surrounding context explicit. Navigation text is a projection; exact originals and the ledger remain evidence.

Retrieval creates one primary representation per exact source passage, independently of task membership. It returns current task associations, their event IDs, and any explicit content spans. Source namespaces keep imported Codex history separate from native source sequences; chronological views sort within those namespaces rather than by task filename. Association spans refer to the named event's intent text; search passage offsets refer to the returned Markdown file. Parent namespace checks, source validation, projection hashes, and truthful keyword/hybrid fallback reporting remain enforced.

## Review and repair

`pocket_task_inspect` exposes bounded navigation pages, the ledger revision, and a work-state `reviewToken`. Task detail includes per-command assignments and lifecycle assessment history. Select `taskId`, `eventId`, or `decisionId` for exact detail; `offset` and `limit` page larger collections. `pocket_task_change` applies a concrete explained assign, move, split, merge, work, or retention operation against the inspected revision/token and regenerates task projections. The token tolerates passive recording of the caller's native tool messages, while new requests, deliveries, commands, semantic decisions, lifecycle changes and repairs invalidate it. Numeric revision-only callers retain strict checkpoint comparison. Split and merge preserve unrelated memberships and spans. Originals and original task intent are not rewritten.

`pocket_task_propose` prepares a semantic proposal without committing it or dispatching work. Historical membership repairs require the user's authorization of the concrete proposal. Missing historical intent cannot be invented by the classifier.

## Migration and verification

The rollout separates ownership consolidation, durable provenance, shadow interpretation, and live ledger projections. Shadow assignments carry `authority: proposal`; source-aligned comparisons are written separately from the legacy archive. The shadow runner refuses a live ledger.

Live migration adopts explicit archive and checkpoint memberships as legacy decisions. Old closed groups become archived navigation with conservative open work state, rather than asserted completion. Ungrouped historical sources and missing provenance remain unknown. Shadow semantic proposals do not silently become authoritative historical memberships. Migration is idempotent, preserves old files, and never submits historical requests or delegate commands.

The automatic lifecycle workflows run an actual Pi working agent that never invokes task-management tools, while independently replaying the external classifier. They cover verified completion, unsupported completion claims, failed tools, ordinary and native questions, actual versus private voice delivery, archive capacity, stale assessments, request constraints/content spans, and real MCP repair concurrency.

Focused workflows also exercise actual SQLite storage, Pi SDK events, native MCP calls, exact source writes, QMD/MCP retrieval, late reports, reused delegates, current versus historical voice context, operational inputs, archived-task corrections, multi-task spans, multiple consumed request origins, stale results, uncertain input, restart windows, identical same-timestamp inputs, delivery reconciliation, and parent isolation. Synthetic provider responses establish orchestration behavior. Authenticated classifier quality, physical-device voice behavior, and optional live GGUF inference remain unmeasured. Full suites belong to CI.
